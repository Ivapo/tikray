### Phase 1 exit gate — 2026-08-16 — **PASSED**, and gate item 5's two measurements

Items 1–4 run as 16 assertions in `tests/gate.rs`; items 1–4 and the linter are
green, and item 5 was run by a human in iTerm2 on a Retina Mac.

**Measurement 1 — `window_size()` reports real pixels here.** The `auto` fallback
is *not* the primary path. A 64×48 source emitted
`inline=1;width=64px;height=48px;preserveAspectRatio=1`. §2.6's warning to
"assume the fallback is a live path" did not fire, and §2.6 carries a dated
`CORRECTED` note saying so, because a Phase 2 implementer planning around the
`auto` branch would be planning around the uncommon case. The branch stays
reachable and tested: any process without a controlling terminal takes it,
including `cargo test`'s own `--force` run.

**Measurement 2 — the viewport is in device pixels, not display points. OQ-7
resolves negatively.** An image wider than the window occupied approximately the
full window width, not about half. No divisor is needed in §2.6 and Phase 2 does
not inherit the problem. Recorded as the round-3 reviewer asked, having been
unable to settle it themselves for want of a controlling terminal.

Item 5's visual half also confirmed: PNG and JPEG each drew the correct picture,
an over-wide image appeared whole and undistorted, and a 16×16 icon appeared
small rather than blown up to fill the window — the never-upscale rule holding in
the terminal and not only in the arithmetic.

**Evidence the gate has teeth, beyond passing.** `load` was mutated to §2.8's
row-2 construction — `ImageReader::open(p)?.with_guessed_format()?` — and
exactly one assertion failed, `gate3_a_text_file_named_png_is_undetermined_not_corrupt`,
with `Decoding(... Png ... InvalidSignature)`: the same "corrupt PNG" outcome
round 2's B3 finding measured. So gate item 3's asserted distinction is real
externally visible evidence of which construction shipped, rather than an
assertion that happens to pass.

Two deliberate departures from the phase's file table, both argued from the spec
rather than convenience: `src/lib.rs` exists because §2.2 makes the library the
product and items 1–3 can only reach `fit`/`sequence`/`load` through a lib
target; `README.md` exists because Phase 1 ships user-facing CLI behaviour and
§6's close-out hook wants documentation or a logged gap.

### Round 2 — Phase 1 only — 2026-08-16 — clean-room reviewer (resumed) — **NOT READY**

One new blocking finding, and the best catch of the review because it came from
compiling rather than reading:

- **B3 — §2.8's stated error taxonomy was unreachable through the mechanism
  §2.8 named.** `ImageReader::open(p)?.with_guessed_format()?` reads as content
  detection, but `open` seeds the format from the path extension and
  `with_guessed_format` is `self.format = format.or(self.format)` — a failed
  guess keeps the extension's answer. Measured: a text file named `.png` was
  refused as `Format error decoding Png: Invalid PNG signature`, i.e. as a
  corrupt PNG, which is precisely the outcome §2.8 promised it would not be and
  gate item 3 asserted against. The likely failure mode was an implementer
  weakening the gate to match the library. **Resolved** by naming
  `ImageReader::new(BufReader::new(File::open(p)?)).with_guessed_format()?` and
  rewriting §2.8 around a three-row table of all three constructions, with the
  trap marked as a trap.

The five `fit` literals were re-derived independently and all reproduce. The
author's own in-flight correction was confirmed: `(3,3)` into `(1,100)` gives
`scale = 1/3` and `round(1.0) = 1`, so the `max(1, …)` floor never fires; the
replacement `(10,3)` into `(1,100)` computes `round(0.3) = 0` and does exercise
it. No case sits on a rounding tie, so the literals are independent of the
rounding mode. Version pins confirmed current, not merely existing: `image`
0.25.10, `base64` 0.23.1, `clap` 4.6.6, `crossterm` 0.29.0.

Three non-blocking findings, all accepted: §2.6's zero-check was justified by a
hedge when crossterm's documentation states it outright ("may not be reliably
implemented or default to 0"; unix *unused*; Windows not implemented);
`window_size()` reads `/dev/tty` rather than stdout, so gate item 4's `--force`
assertion is now prefix-only; and Phase 2's prose still said "RGBA buffer" after
the N7 fix.

### Round 1 — Phase 1 only — 2026-08-16 — clean-room reviewer with repo access — **NOT READY**

**Round 0 (asked once for this episode, not re-litigated after).** *Does this
phase produce the observable, and is it the right one?* Yes — Phase 1 draws a
PNG or JPEG inline in iTerm2, which is literally the first half of the recorded
observable, so it produces one rather than having to argue it does not; and it
is the right first one because it is the shortest path from no code to anything
visible, and it retires the project's largest unknown (does the inline protocol
display what we emit, at a sane size, in this terminal) before SVG, conversion
or a TUI are stacked on it. Recorded caveat: **Phase 1 in isolation duplicates
`chafa`/`timg`** — this project's reason to exist lives in Phase 3, so a Phase 1
that shipped alone would be a nicer-packaged version of a tool the user already
has. That is an argument for keeping Phase 3 non-optional, not against building
Phase 1 first.

The repo had no code at this round, so there were zero `file:symbol` citations
to check and grounding rested entirely on external facts. Those were verified
against primary sources (iTerm2's Inline Images Protocol page, `docs.rs/image`).

Two blocking findings:

- **B1 — the display path as specified would have downloaded the file instead of
  showing it.** §2.3 described "print the escape sequence" while never
  enumerating a single `File=` argument, and `inline` **defaults to 0**: iTerm2's
  documentation says the file "will be downloaded with no visual representation
  in the terminal session." Implemented from the spec alone, that is a silent
  download, exit 0, nothing displayed — exactly the failure §1 names when it
  refuses to treat the escape sequence as the observable. The spec identified the
  hazard and then omitted the one argument preventing it. **Resolved** in §2.3 by
  making `inline=1` mandatory, pinning the full argument string, and asserting the
  byte in gate item 2.
- **B2 — the gate's "outside iTerm2 → exit non-zero" clause named no detection
  mechanism, and the candidates disagree.** Four inconsistent environment signals
  plus iTerm2's own Feature Reporting protocol, differing in behaviour (only
  `LC_TERMINAL` survives ssh; none survive plain tmux; WezTerm implements the
  protocol but is not iTerm2) and by an order of magnitude in cost — which also
  changed whether the phase was one plan-mode pass. **Resolved** by new §2.7:
  tty check plus `TERM_PROGRAM`/`LC_TERMINAL`, Feature Reporting recorded as
  rejected *with its trade-off written down* rather than silently omitted, and
  `--force` as the escape hatch for the known false negatives.

Nine non-blocking findings, all accepted: the gate had nothing machine-checkable
and its sizing clause was self-certifying (the implementer chose the default it
was checked against, so it could not fail); "fits the window" was satisfiable by
upscaling a 16×16 icon to fill the screen; OQ-3's option list contradicted the
gate meant to resolve it; §2.3 never mentioned the protocol's sizing arguments
exist; the supported-input allowlist was unstated while §2.4 assigned that duty
to a gate that did not discharge it; extension-vs-content detection was Phase 1's
choice with Phase 2 already constraining it; the buffer type was unnamed and
§2.1's "RGBA" contradicted §2.3's "no colour-approximation anywhere"; the phase
named no files, signatures or dependency versions, against conventions §3; the
JPEG→RGBA→PNG round-trip was presented as forced when it is chosen; OQ-5 named
no phase, against conventions §4; and §2.4 overstated WebP (encode is
lossless-only).

**Notable adjudication — a suggestion resolved differently.** The reviewer
proposed delegating sizing to the terminal with `width=100%;height=100%`,
observing it would shrink the phase measurably. Rejected in favour of computing
`px` in §2.6, because *filling is not fitting*: the protocol fills "as much as
possible without stretching", which upscales, and a 16×16 favicon would fill the
window as a screenful of blurred squares. Round 2 agreed on re-review — the
suggestion would have reintroduced exactly the case gate item 5 now names.

**Numbers this round's fixes introduced**, re-derived at round 2 and recorded so
a later round can trust them: `fit` maps `(800,600)/(1600,1200) → (800,600)`,
`(4000,1000)/(1000,1000) → (1000,250)`, `(10,3)/(1,100) → (1,1)`, and unreported
or zero-axis viewports → `None`.
